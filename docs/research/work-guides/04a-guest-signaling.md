# 04a · 게스트 시그널링을 렌더 스레드 밖으로

**상태: PLANNED.** 01을 먼저 적용하면 로컬 리스너 주소가 확정된다. 접속 수명·취소 규칙을 먼저 적는다.

- **소스 확인:** [`ConnectScreenMixin`](../../../src/client/java/kfc/udp/client/mixin/ConnectScreenMixin.java)의 접속 시작에서 [`WebRtcClient.start`](../../../src/client/java/kfc/udp/client/webrtc/WebRtcClient.java)가 `connectPairSignaling`을 동기로 호출한다. [`WebSocketClient`](../../../src/client/java/kfc/udp/client/webrtc/WebSocketClient.java)의 연결에는 DNS·TCP·WebSocket 응답 대기가 있다. 클라이언트에는 `signalScheduler`가 있다. 현재는 페어 WebSocket 연결을 먼저 시작하고, 로컬 Minecraft 소켓을 받은 뒤 로비에 조인 알림을 보낸다. 방장은 그 알림을 보고 게스트 페어 세션으로 들어온다.
- **추정:** 사용자의 체감 멈춤과 실제 상한은 환경별 DNS·서버 상태로 달라진다. 연구 문서의 최대 대기 계산은 현행 타임아웃에서 추론한 것이다.
- **제안·최소 변경:** 로컬 리스너 시작 후 페어 시그널링 연결을 기존 시그널러 스레드에 예약한다. **페어 WebSocket이 준비되기 전에는 로비 조인 알림을 보내지 않는다.** 연결 준비를 나타내는 별도 latch를 두고 로컬 Minecraft 소켓을 받은 스레드에서 기다리되, 기존 `awaitOrMcCancel` 방식으로 조기 Minecraft 핸드셰이크·로그인 바이트를 보존하고 화면 취소를 즉시 감지한다. UI 취소·재접속이 이전 작업의 완료 콜백을 새 세션에 전달하지 못하게 세션 식별자 또는 취소 상태를 확인한다.
- **정적 게이트:** 페어 준비 → 로비 조인 알림 → 호스트 페어 진입의 순서를 지킨다. 시작·취소·재시도·실패의 소유자를 적고, 대기 중 MC 바이트 보존, WebSocket 연결 중 취소·닫기, 포트 누수·중복 접속·늦은 콜백을 검토한다. 메시지 JSON과 peer 이름은 변경하지 않는다.
- **계약 시험 게이트:** 연결 완료를 지연·실패·취소할 수 있는 가짜 WebSocket으로, 로비 조인 알림이 페어 준비보다 먼저 나가지 않는지 확인한다. 준비를 기다리는 동안 들어온 Minecraft 바이트가 정상 연결 뒤 한 번만 전달되는지, 취소 시 리스너·진행 중 WebSocket이 닫히고 뒤늦은 완료 콜백이 새 세션에 영향을 주지 않는지도 검사한다.
- **빌드 게이트:** 1.21.x·26.x 대표 빌드와 위 지연·취소 계약 시험을 통과한다.
- **실행 게이트:** 방장·게스트 두 Minecraft 인스턴스에서 시그널링 서버 정상·지연·불가 각각의 화면 응답, 실패 표시, 취소 후 리스너 종료, 재시도를 확인한다. 실제 접속·재접속과 조기 MC 바이트가 있는 연결을 기록한다.
- **되돌리기:** 시그널링 예약 지점만 동기 경로로 되돌릴 수 있어야 한다. 중복 작업이 남는다면 출시는 보류한다.
